  The 16 KB page-size dialog — not a crash, not our bug. It's Android flagging
  that libmlkit_google_ocr_pipeline.so, bundled inside the
  com.google.mlkit:text-recognition:16.0.0 dependency (app/build.gradle:51), has
  a LOAD segment that isn't 16 KB-aligned. It only surfaces because the app is
  debuggable (the dialog says so explicitly) and won't appear for end users on a
  properly built release.

  I checked upstream: this is a known, currently-unresolved issue across several
  ML Kit modules (face-detection, barcode-scanning, text-recognition,
  image-labeling) — see googlesamples/mlkit#975
  (https://github.com/googlesamples/mlkit/issues/975) and #987
  (https://github.com/googlesamples/mlkit/issues/987). No fixed version of
  text-recognition exists yet; the one workaround people found (forcing a newer
  CameraX dependency) fixes a different bundled .so
  (libimage_processing_util_jni.so), not this one. So there's nothing to
  responsibly patch today — it's an open upstream tracking item, not a blocker
  for alpha testing.

  because the launcher icon PNGs in
  UMAssisted-private/app/src/main/res/mipmap-*/ are 12-byte placeholder text

  assembleRelease.

● japanglify's key patterns: a generation counter that invalidates stale chained
  callbacks (their copyPipelineGeneration), and explicit instance lifecycle 
  cleanup on service teardown (their onDestroy nulling instance). Both apply
  directly to UMAccessibilityService — it has multi-step handler.postDelayed
  chains (sweep: 5 hovers → scroll → capture; career exit: hamburger → menu →
  confirm) with no protection against a second command interleaving mid-chain,
  and instance is set in onServiceConnected but never cleared, so a stale
  reference could survive unbind. Porting both now.
