  INTERACTION EXAMPLES
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Scenario A: Fast reader with tremor
    1. Pace starts at Normal (5.0) → dwell 3000ms, slide 260ms
    2. Drag Dwell left to 1500ms (reads fast)
    3. Drag Slide right to 500ms (tremor needs slower transitions)
    4. Pace recalculates: (1500/3000) × (260/500) ≈ 0.87 (slower than normal)
       ✓ Combined effect: shorter dwell + longer slide = safer sweep

  Scenario B: Slow reader, no motor issues
    1. Pace set to Slow (3.0) → dwell 6000ms, slide 520ms
    2. Leave both at pace-derived values (not overridden)
    3. Pace remains at 3.0 (fully coupled)
       ✓ Simple—one slider controls everything

  Scenario C: User wants quick glance + careful finger control
    1. Pace set to Fast (8.0) → dwell 1500ms, slide 130ms
    2. Drag Slide right to 400ms (wants more control than pace auto-set)
    3. Dwell stays at 1500ms (not overridden)
    4. Pace recalculates: (1500/3000) × (260/400) ≈ 0.325 × 0.65 ≈ 3.25
       ✓ Much faster than normal, but less rapid transitions

  UserSettings {
    pace: 5.0                    // 1.0 (slow) to 10.0 (fast)
    dwell_ms: null               // null = pace-derived, else override
    slide_ms: null               // null = pace-derived, else override

    // Derivation:
    effective_dwell = dwell_ms ?? (3000 × pace / 5.0)
    effective_slide = slide_ms ?? (260 × pace / 5.0)

    // When user overrides dwell or slide:
    pace = (effective_dwell / 3000) × (260 / effective_slide)
  }

  UserSettings.kt now exposes one knob (SweepPeriodMs) instead of

    speed
     ^
     │      ╱‾╲              ╱‾╲              ╱‾╲
     │     ╱   ╲            ╱   ╲            ╱   ╲

    Velocity → 0 at each facility (natural "lingering," not a timed
    dwell); velocity peaks between facilities (natural "slide," not a
    separate setting). Nothing to configure per-phase — the shape does
    both jobs from one number.

  WHY THE DWELL FLOOR IS GONE
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    Old model:  sweep highlights F3 → user must notice + act within the
                dwell window → sweep moves on, chance is gone.
                (WCAG 3s-timed-content floor made sense here.)

    Actual model: user says the facility's NAME whenever they notice it —
                even after the sweep has moved past it three times.
                Selection is resolved by matching the utterance to the
                name, not by "what's currently lit up."
                → No deadline exists to protect with a floor.
                → Speed is purely a comfort/aesthetic preference now.

● For confirming a dispatched action actually had an effect, I'd rank these
  pretty differently on cost vs. signal quality:

  - Screen-content diffing (before/after screenshot, or better, per REQ-M3's
  takeScreenshotOfWindow) is the strongest and cheapest option — zero new
  permissions, already fully wired into the existing OCR/matching pipeline, and
  it tells you what changed, not just that something did. I'd make this the
  primary post-dispatch confirmation signal.
  - Audio output monitoring is much higher cost for weaker signal: Android has
  no lightweight "listen to what's playing" API — you'd need
  MediaProjection-based AudioPlaybackCapture (API 29+), which requires a
  user-facing screen-capture consent prompt and sits awkwardly against REQ-S1's
  minimal-permission stance. And even captured, a generic UI chime tells you a
  button fired, not which one or that the right thing happened — much weaker
  than a screenshot diff. I'd defer this unless screen-diffing alone proves
  insufficient somewhere.
  - Accelerometer/haptic is cheap (no special permission) but low-specificity —
  it tells you the OS registered some touch, not that the game reacted
  correctly. More useful as a "was this a genuine physical tap" cross-check for
  REQ-M8's raw-touch-capture case than as an app-state confirmation.

  My recommendation: formalize screen-diffing as the required post-dispatch
  check (pairs naturally with REQ-SF7's "verify before dispatch" with a "verify
  after dispatch" counterpart), and leave audio/accelerometer as
  noted-but-deferred ideas rather than committing to them now. Want me to write
  that up as a requirement, or keep talking through the shape of it first?
