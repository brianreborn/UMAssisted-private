  On network access for UMAssisted — this fits naturally with what we'd already
  scoped. The AccessibilityService approach (consolidating taps, auto-advancing
  no-choice screens, alternate input triggers) needs zero network access to work
  — it only needs to read the screen's accessibility tree and dispatch gestures
  locally. I'll treat "no INTERNET permission in the manifest" as a hard
  requirement, not just a default:

  - No android.permission.INTERNET in AndroidManifest.xml at all — not "off by
  default," genuinely absent, so it's structurally impossible for the app to
  phone home even if some future code tried.
  - That also rules out: crash reporting SDKs, analytics, remote config,
  auto-update checks, cloud-synced settings — all common "small" ways network
  access creeps into an app. Settings/profiles should be local-only (or
  exported/imported manually as files if you ever want to share a config).
  - This also closes off a class of concern with the root-based fallback path we
  discussed earlier: no listening sockets, no remote-trigger mechanism.

  I'll carry this as a standing constraint for every future requirement we
  scope, not just a one-time note. Want me to start capturing these decisions
  (name, platform, mechanism, no-network constraint) into an actual requirements
  doc, or keep going conversationally for now?

● Pushed. This is a solid architectural simplification — captured as:

  - REQ-M3 revised: dropped general real-time OCR in favor of matching the live
  screen against a pre-built offline corpus built from existing
  community/datamined event databases. That turns "read arbitrary text reliably"
  (hard, uncertain accuracy/latency) into "classify against a known, finite
  set" (much more tractable).
  - One matching system now does double duty: it answers REQ-M3's "what's on
  screen" and becomes the natural identity key for REQ-A4's "which decision
  point recurred" — they were always the same underlying question.

  the readout text is the corpus's already-known dialog text, not something
  extracted from pixels — pushing REQ-T4's 1.0-eligibility further in the "yes,
  achievable" direction.

  database to source the corpus from (and any licensing considerations, since
  the underlying text is still Cygames' IP regardless of who catalogued it), how
  to keep it current as new events ship, and how robust the offline matching

● Let me address the harder question directly, since "trust the code" isn't a
  real answer here.

  The argument: I can't prove the test service's code is bug-free, so the
  ethical claim can't rest on correctness at all — it has to rest on structural
  constraints that hold even if the code has a bug. Concretely, for
  chain-of-custody-of-control:

  1. Single trigger surface, and nothing else exists in the code. The only path
  to dispatchGesture() is the onClick handler of one on-screen button you tap —
  no timers, no listeners, no background triggers. Not disabled — absent. A bug
  can only make that one button misbehave; it can't make anything else in the
  codebase decide to fire, because nothing else can decide anything.
  2. Two-step confirm, mirroring REQ-V4's existing pattern. First tap arms and
  previews exactly what's about to happen ("about to dispatch one tap at (x,y) —
  confirm?"); second tap fires. Two independent deliberate actions from you,
  not one.
  3. Staged validation before touching anything real. Prove the mechanism
  behaves correctly against a zero-stakes target first (a blank test screen, or
  Settings) — only after that, point it at Umamusume, and even then only at an
  inert, reversible target (Back), never anything consequential.
  4. You stay physically present and watching for the entire test. Not left
  running unattended — a bug is caught and stoppable within seconds, not hours,
  because you're the one holding the phone.
  5. Small enough to actually read. Not a black box trusted on faith — short
  enough that you read every line before it's installed.
  6. Installed, run once, uninstalled. Not a standing service that persists as
  risk after the test.

  None of that proves the code is correct. It proves that even if it isn't, the
  blast radius is bounded to one button, caught by a human watching in real
  time, against a target that doesn't matter. Let me add both this and the
  overlay requirement to the doc.

● Good, let's dig into the mechanics. The three known implementations actually
  cluster into meaningfully different technical strategies, and comparing them
  sharpens REQ-M3 in a real way:

  1. UmatoMusume — OCR + fuzzy string matching. Captures the screen, runs OCR,
  then does fuzzy/string-similarity matching against the known event database
  rather than trusting OCR's raw output as the answer. This is the key trick:
  OCR errors don't need to be zero, because the OCR text is only ever used to
  find the nearest match in a small, bounded, known set — not read as ground
  truth.

  2. Umaplay — YOLO object detection + PaddleOCR + a classifier. Detects 40+ UI
  element types as objects (buttons, cards, stat badges), reads numeric/text
  fields via OCR with fallback logic, and classifies button states with a small
