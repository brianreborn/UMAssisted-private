## The hard part: `REQUIREMENTS.md#…` must actually land

GitHub (and most Markdown renderers) only auto-anchor **headings**, not bold list items like:

```markdown
- **REQ-M3 — Screen understanding falls back…**
```

So today:

- `REQUIREMENTS.md#5-core-mechanism` works  
- `REQUIREMENTS.md#req-m3-…` does **not**

### Fix options (pick one)

**A. Explicit HTML anchors next to each REQ (recommended for this repo)**  
```markdown
- <a id="req-m3"></a>**REQ-M3 — Screen understanding…**
```
Stable, short, case-insensitive fragments: `#req-m3`, `#oq-1`.  
Pros: works on GitHub, no renumbering pain. Cons: slight visual noise in source (or put anchors on their own line).

**B. Promote each REQ to a heading**  
```markdown
#### REQ-M3 — Screen understanding…
```
Pros: free GitHub slugs. Cons: TOC becomes huge; slug changes if the title text changes unless you pin IDs.

**C. Generated HTML page** with real `id`s, graph links to that HTML, Markdown stays source of truth.  
Pros: best UX. Cons: second artifact to keep in sync (fine if CI-generated).

**D. Line-number links** (`#L159`)  
Fragile under every edit — skip for a living draft.

**Recommendation:** **A** (or A+C). Stable `#req-m3` IDs match how you already talk about requirements, and graph nodes can hardcode `id = lower(REQ-id)`.

## How to render the graph

Three tiers, increasing complexity:

### 1. Static Mermaid / Graphviz in-repo (lightest)
- Script parses `REQUIREMENTS.md` → emits `docs/requirements-graph.md` with Mermaid `flowchart` / `graph`.
- Clickable nodes: Mermaid supports link syntax to `#req-m3`.
- Pros: lives next to the public doc, no server, fits REQ-P3 (requirements repo only).  
- Cons: dense graphs get unreadable; filtering is limited.

### 2. Interactive HTML (best “matrix + graph” experience)
- Build a single static page (e.g. **D3 force graph**, **Cytoscape.js**, **vis-network**, or **Observable**-style).
- Left/side panel = **matrix** (filter by family, status, milestone).
- Main canvas = **graph**; click node → opens `REQUIREMENTS.md#req-m3` (GitHub blob URL) or in-page panel with excerpt.
- Generated from Markdown so the graph never drifts.

Example node payload:
```json
{
  "id": "REQ-M3",
  "family": "M",
  "title": "Screenshot-based recognition…",
  "href": "https://github.com/brianreborn/UMAssisted/blob/master/REQUIREMENTS.md#req-m3",
  "status": "active",
  "section": "5"
}
```

### 3. Matrix-first, graph secondary
A **traceability matrix** table is often more useful day-to-day than a full force graph:

| REQ | Depends on | Resolves | Gates | Status |
|-----|------------|----------|-------|--------|
| REQ-V12 | REQ-V4, REQ-V11 | OQ-30 | — | decided |
| REQ-QA2 | REQ-A10, REQ-V9 | — | 1.0 final | open verify |

Each cell is a link. Graph is a *view* of the same edge list, not a second source of truth.

## Architecture that fits this project

```
REQUIREMENTS.md  (canonical prose + stable #req-* anchors)
       │
       ▼ parse (script, CI or manual)
  requirements-graph.json  (nodes + edges)
       │
       ├─► requirements-matrix.md   (tables, GitHub-readable)
       ├─► requirements-graph.mmd   (Mermaid)
       └─► requirements-graph.html  (optional interactive)
```

**Source of truth stays the Markdown** — same rule as REQ-OQ1. Graph/matrix are projections.

**Edge authoring options:**

1. **Inferred** — regex for `REQ-X`, `Resolves OQ-N`, `see REQ-Y` (works today, noisy).  
2. **Structured front-matter per REQ** (cleaner long-term):
   ```markdown
   <!-- req id=M3 depends=M1,S1 resolves=OQ-2 gates= -->
   - <a id="req-m3"></a>**REQ-M3 — …**
   ```
3. **Hybrid** — infer first, maintain only high-value edges (`depends_on`, `gates`) explicitly.

For a living draft, **hybrid** is enough: infer cross-refs for “mentions,” curate `depends_on` / `gates` for the matrix that actually matters.

## Design choices worth deciding before building

1. **Audience** — GitHub readers only, or local HTML for you? (Public requirements repo → static artifacts only; no app backend.)
2. **Primary view** — force graph for exploration, or matrix for “what’s blocking what?”
3. **OQs in the graph?** — yes for BLOCKING/OPEN; hide RESOLVED by default or fade them.
4. **Cross-cutting nodes** (`REQ-S1`, `REQ-A5`, `REQ-A11`) — show as hubs, or as filters so they don’t spiderweb everything?
5. **Anchor strategy** — commit to `#req-m3` / `#oq-1` now so links never churn.
6. **Generation** — one Python/Node script checked in vs. manual Mermaid (manual dies quickly at 70+ nodes).

## The shape

- **Tree (layout / nesting):** where a requirement *lives*  
  `§5 Core Mechanism → REQ-M3 → bullets / residual OQs`
- **Graph (arrows):** how requirements *relate*  
  `REQ-T5 → depends on → REQ-A4`  
  `REQ-M5 → resolves → OQ-2`  
  `REQ-QA2 → gates → 1.0 final`

```

├── REQ-V1
│   └── REQ-V5  ──────────────┐
│       └── REQ-V6            │  (extends / raises bar)
├── REQ-V4 ◄──────────────────┼── REQ-V12  (confirmation form)

         │
         └── always-visible overlay ◄── REQ-A10  (cross-section arrow)
```

Parent lines = document structure.

## Why this works for UMAssisted

| Pure tree | Pure force graph | Tree + arrows |
|---|---|---|
| Loses “REQ-V2 needs REQ-S1” | Loses § structure / reading order | Keeps both |
| Cross-links become fake nesting | Hubs (A4, M3, S1) explode the layout | Cross-links stay as arrows |
| Matches the MD outline | Feels exploratory but hard to scan | Outline = backbone; arrows = load-bearing |

Your doc is **already a tree** (sections → REQs). The interesting part is the **graphness on top** — dependencies, resolves, gates, cross-cuts.

## Edge kinds (keep few)

Too many arrow types = spaghetti. Start with 3–4:

| Arrow | Style idea | Meaning |
|---|---|---|
| **depends on** | solid | must exist / hold for this to work |
| **resolves** | solid, OQ → REQ or REQ → OQ | decision closed |
| **extends / implements** | dashed | specialization of a parent rule |
| **gates** | thick / milestone color | release blocker |

Cross-cutting hubs (`REQ-S1`, `REQ-A5`, `REQ-A11`) should **not** get 40 spokes drawn always — filter them (“show S1 edges”) or draw them as a **side rail** the tree sits under, with optional highlight.

---

## Layout patterns that match “tree but arrows”

1. **Indented outline + arc links** (side or over the tree)  
   Classic “code map” / dependency-on-outline. Best for GitHub + simple HTML.

2. **Tidy tree (Reingold–Tilford) + curved edges for non-parent links**  
   What people expect from “org chart with extra arrows.” D3 `tree` + second edge layer.

3. **Clustered sections as columns**  
   Each § is a column; REQs stacked inside; arrows cross columns. Good for “architecture vs voice vs QA.”

4. **Mermaid `flowchart` with subgraphs**  
   ```text
   subgraph Voice
     V4 --> V12
   end
   S1 --> V2
   ```
   Subgraphs = tree clusters; `-->` = graph. Limited interactivity, fine as a first shippable view.

Recommendation for a first real artifact: **(1) or (2)** — outline backbone you already know, arrows for the graphness.

- Click **arrow** → optional tooltip (“depends on: no network → on-device STT only”).

- **Draw every textual mention as an arrow** — `REQ-A4` would become unreadable. Curate: structure edges + high-value semantic edges; mentions stay in search/matrix.
